# 部署与运维

## 1. 构建与验证

从 clean checkout 使用 workspace 声明的 Rust 工具链和锁文件：

```sh
cargo build --locked --release -p cofferwired
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
python3 scripts/check_conformance.py --check-report conformance/coverage.json
```

独立 Python 环境和互操作命令见 [`60_一致性验证与独立实现.md`](60_一致性验证与独立实现.md)。

## 2. TLS 与启动

运营者需要准备可由客户端验证的 certificate chain、受限权限的 private key 和独立
SQLite 路径，再按 [`80_配置参考.md`](80_配置参考.md) 的位置参数启动 daemon。私钥不得
放入仓库；终止、supervision、证书续期和 host firewall 由部署平台负责。

`cofferwired` 始终自行终止 TLS，不提供明文 HTTP listener。反向代理只支持两种拓扑：

- TCP/TLS passthrough：原样转发 TLS bytes，由 daemon 终止 TLS；
- TLS bridging：代理终止客户端 TLS，再与 daemon 建立独立 TLS 连接。

代理必须保持 binary body、Content-Type、WebSocket subprotocol 和 body/time bounds。协议认证
绑定解码后的协议 bytes，不绑定 TLS identity、HTTP headers 或 WebSocket session；按 credential
计费的限流因此不受代理源地址或连接复用影响。但连接级限制按 daemon 实际看到的连接和并发
命令计数，代理复用会改变客户端侧的有效 admission 行为，upstream pool 必须据此配置。

`BIND_ADDRESS` 是单个 `SocketAddr`。首选一个进程绑定一个地址；可在目标平台验证 IPv6
wildcard 的 dual-stack 行为，或由同时监听 IPv4/IPv6 的代理转发到单个 daemon。项目没有验证
两个 daemon 进程并发共享同一个 SQLite 文件，即使 SQLite 本身支持多进程锁，也不得把该
部署形态宣称为受支持配置。

## 3. 健康与监控

`/healthz` 只用于 process liveness。至少还应由外部 synthetic client 验证 TLS、frame
往返和 durable queue 操作。指标只允许聚合 bucket，禁止 queue/capability/principal、
content、key 和可避免的跨会话关联值；隐私约束见
[`docs/spec/12`](../spec/12-privacy-considerations.md)。

## 4. 备份与恢复

当前数据库使用 SQLite rollback journal，而不是 WAL。仓库测试只证明所有 writer connection
关闭后复制单个数据库文件，并在 fresh process 中恢复，可以保留 queue/blob state 和
`queue_replays`/`blob_replays` 的 exact-retry 语义。未验证 daemon 运行或事务进行中的热拷贝；
如需在线备份，应先引入 SQLite online backup API，并用现有 crash/restore suite 验证。

受支持的备份流程：

1. 停止 `cofferwired` 并等待进程退出，确保 `DATABASE_PATH` 没有打开的连接；成功响应此前已
   完成 durable commit，无需额外 flush。
2. 复制 `DATABASE_PATH`。稳定状态不应存在需要配套复制的 journal；若仍有 `-journal`，继续
   等待进程完全退出后重试。
3. 重启原数据库上的 daemon；备份文件成为独立的 point-in-time snapshot。

受支持的恢复流程：

1. 停止使用目标路径的 daemon。
2. 把备份复制到 `DATABASE_PATH`，或直接把该配置指向备份文件。
3. 启动 daemon；[`DurableRelay::open`](../../crates/cofferwire-relay/src/durable.rs) 会执行与
   schema migration 测试相同的升级路径。
4. 恢复正常流量前，用已知 queue 的 `FETCH` 等只读客户端请求验证行为。

恢复会丢失快照产生后才提交的命令，这是备份新鲜度边界，不是 durability 违规。

## 5. 保留与删除

queue deletion 与 blob deletion 的物理效果不同：

- 过期 message 在 queue 下次被访问时，由 `discard_expired` 执行 SQL 删除；
- `DeleteQueue` 删除 queue row，并由开启的 foreign keys 在同一事务级联删除 message rows；
- [`DurableRelay::delete_blob_tx`](../../crates/cofferwire-relay/src/durable_blob.rs) 只把授权
  grant 标为 deleted，不删除 `blob_chunks`、`blob_objects` 或 `blob_uploads`；当前没有 blob
  ciphertext GC。

SQLite 使用 rollback journal，且 daemon 没有开启 `secure_delete`。逻辑删除后的 bytes 可能
留在 free pages，直到页面复用或 `VACUUM`；旧备份也不会随 live database 删除而变化。需要
物理清除时，运营者必须评估 `PRAGMA secure_delete = ON` 的额外写入成本，或在批量删除后停机
执行并验证 `VACUUM`，同时轮换或销毁仍含数据的历史备份。

因此 TTL 是可用性策略，不是安全擦除保证；“从 active service 删除”和“从所有存储副本
清除 bytes”必须作为不同承诺。对 blob，当前实现连主动删除 ciphertext 都不能保证，必须
明确披露，不能用运维步骤掩盖这一实现缺口。

## 6. 故障响应

- storage `Busy` 可有限重试；`ReadOnly`、`Full`、`Io`、`Corrupt` 要先修复底层状态。
- 请求在 durable response 前断开时，client 重试完全相同的已认证 bytes。
- relay 丢失时，从 authenticated recovery material 在新 relay 重建 queue，sender 重传
  未确认 application update；应用 identity 不随 relay 改变。
- 疑似漏洞通过 [`SECURITY.md`](../../SECURITY.md) 的私密渠道处理，不在公开 issue 泄露
  未修复复现细节。

## 7. 真实试点与外审

### 7.1 Family-Tree v1 真实试点（#25）

试点只使用 synthetic family-tree records，公开结果不得包含真实姓名、日期、关系、凭证、
private key、capability、queue ID、IP 地址或原始应用/relay 日志。参与方包括三台具有独立
durable client store 和 queue principal 的物理设备、两个分别由不同运营者控制且 endpoint、
数据库、凭证和配置均独立的 relay，以及只记录聚合结果和 digest 的协调者。

所有参与方使用同一个完整 Git commit，并记录 binary/config SHA-256。依次验证 delayed
convergence、duplicate delivery、至少 24 小时真实离线、suspend/resume、lost notification、
不复制数据库的 relay replacement、禁网状态下的 signed history bundle recovery，以及精确
绑定 update bytes 与 signer 的 application receipt。Relay ACK 不得计作应用回执；不能用加速
协议时钟代替 24 小时 wall-clock observation。

从 [`family-tree-v1-result.example.json`](../../scripts/fixtures/family-tree-v1-result.example.json)
复制本地结果到 `docs/temp/family-tree-pilot-v1.json`，填完后执行：

```sh
python3 scripts/validate_family_tree_pilot.py docs/temp/family-tree-pilot-v1.json
```

validator 检查结构、同一 revision、场景完整性、独立运营者、物理设备、敏感字段和参与者
attestation；它不能证明人物、硬件、时长或观察真实，仍需参与者公开确认。

### 7.2 外部密码学与协议审查（#27）

reviewer 必须独立于设计和实现工作，并具备 applied cryptography、binary protocol 或
distributed authorization system 审查经验。自审、自动扫描报告或实现共同作者不满足门禁。
协调者冻结一个 Git commit，并生成确定性审查包：

```sh
python3 scripts/build_review_bundle.py \
  --revision COMMIT \
  --output docs/temp/cofferwire-review.tar
sha256sum docs/temp/cofferwire-review.tar
```

报告必须逐项覆盖 cryptographic construction、capability lifecycle、queue/blob authorization、
replay/rollback/downgrade、storage deletion/retention、metadata/traffic correlation、DoS/abuse
controls 和 client/relay implementation。潜在可利用且未修复的问题只通过 `SECURITY.md` 的
私密渠道报告。critical/high 必须修复并由 reviewer 验证；medium/low 必须 fixed、附理由接受
或在安全披露后建立公开 follow-up。

从 [`external-review-result.example.json`](../../scripts/fixtures/external-review-result.example.json)
复制结果到 `docs/temp/external-review-v1.json`，并执行：

```sh
python3 scripts/validate_external_review.py docs/temp/external-review-v1.json
```

validator 只能检查范围与 disposition 完整性；维护者仍须核实 reviewer 身份、资格和独立性。

## 8. 发布

发布使用一个完整 candidate revision。把
[`gate-manifest-v1.example.json`](../../scripts/fixtures/gate-manifest-v1.example.json) 复制到
`docs/temp/gate-manifest-v1.json`，十项 gate 的状态、revision、公开证据位置和 SHA-256 都必须
完整；单纯声明或 checkbox 不算通过。

在两个独立 provision 的 clean Linux 环境签出相同 revision，以仓库 Rust/Cargo 版本和
locked dependencies 构建 `cofferwired` 与 `cofferwire-line-relay`。记录工具版本、target、命令
和两组 digest；binary bytes 不一致时停止发布，不得任意选择一份为 canonical。

使用任一份相同 binary 构建确定性工件：

```sh
python3 scripts/build_release_artifacts.py \
  --revision COMMIT \
  --output-dir docs/temp/cofferwire-1.0 \
  --binary cofferwired=target/release/cofferwired \
  --binary cofferwire-line-relay=target/release/cofferwire-line-relay \
  --gate-manifest docs/temp/gate-manifest-v1.json \
  --pilot-evidence docs/temp/family-tree-pilot-v1.json \
  --review-evidence docs/temp/external-review-v1.json
```

在两个 clean directory 重复构建并逐行比较 `SHA256SUMS`。随后使用仓库外 release-only
OpenSSH Ed25519 key 对 `SHA256SUMS` 签名，通过独立认证渠道发布 `allowed_signers`，再运行：

```sh
python3 scripts/validate_release_candidate.py \
  docs/temp/cofferwire-1.0 \
  --allowed-signers /path/to/allowed_signers \
  --signer cofferwire-release
```

验证通过后才可原样发布 artifact、在 release notes 记录公开 URL 与 checksum、于 candidate
commit 创建包含 checksum 的 annotated `v1.0.0` tag、推送 tag，并重新下载公开工件独立验证。
缺 #25 或 #27 的真实外部证据只能 rehearsal。发布完成且公开工件已独立验证后，删除整个
`docs/temp/`；该目录不得成为证据的唯一存档位置。
